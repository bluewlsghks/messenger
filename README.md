### 🏗️ 구조

```text
Thymeleaf / JavaScript
        │
        ├─ REST / STOMP
        │       ↓
        │   Controller → Service → Repository / MongoTemplate
        │                              ↓
        │                           MongoDB
        │                     메시지 + pending outbox
        │                              ↓
        │                         Outbox Worker
        │                           ├─ 방별 변경 기록 → 증분 동기화
        │                           ├─ STOMP → 클라이언트
        │                           ├─ 검색 색인 (선택)
        │                           └─ Push 작업 큐 (선택)
        │
        └─ WebRTC → 브라우저 간 음성·영상 전송
                    통화 제어 상태는 서버에서 공유
```

컨트롤러는 요청·응답, 서비스는 업무 흐름과 권한, 저장소는 데이터 접근을 담당하도록 구성했습니다. DTO와 보안·설정 코드를 분리하고, 메시지 변경·프로필·미확인 집계 로직을 컨트롤러 밖으로 이동했습니다. 일부 복합 쿼리는 기존 서비스의 MongoTemplate 구현을 유지합니다.

### 🔍 주요 설계와 문제 해결

#### 1. 재전송으로 인한 메시지 중복 저장 방지

네트워크 오류 뒤 같은 전송 요청이 반복되는 상황을 고려해 **클라이언트 요청 UUID와 부분 고유 인덱스**를 적용했습니다. 메시지와 발행 대기 상태를 같은 MongoDB 문서에 원자적으로 기록하고, outbox worker가 재시도와 버전 조건부 완료 처리를 담당하도록 구성했습니다.

클라이언트의 중복 표시 방지와 서버의 중복 저장 방지를 구분했으며, 재접속 시에는 페이지 단위로 저장된 대화 상태를 대조합니다. 이 구조는 중복 저장과 발행 실패에 대응하기 위한 것으로, 종단 간 정확히 한 번 전달을 보장하는 방식은 아닙니다.

#### 2. REST·STOMP·검색에 일관된 접근 제어 적용

HTTP 요청뿐 아니라 **STOMP 구독과 실제 메시지 수신 단계에서도 현재 멤버십과 채널 권한을 검사**합니다. 발신자 정보는 서버의 인증 정보로 결정하고, 검색 결과 역시 MongoDB의 현재 데이터와 권한을 다시 확인해 전달합니다.

친구 차단이나 채널 권한 변경 이후에도 이전 연결·검색 결과를 통해 정보가 전달되지 않도록 접근 경계를 구성했습니다.

#### 3. 메시지 조회 경계와 동시 변경 처리

동일한 생성 시각의 메시지가 페이지 경계에서 누락되지 않도록 **생성 시각 + 메시지 ID 복합 커서**를 사용했습니다. 수정·삭제는 작성자·대화·현재 버전을 조건으로 원자적으로 갱신해, 오래된 화면에서 보낸 요청이 최신 변경을 덮어쓰지 않도록 했습니다.

읽음 표시와 미확인 메시지 집계도 공통 기준으로 정리했습니다.

#### 4. 다중 탭·다중 서버 환경의 통화 상태 관리

음성·영상은 WebRTC로 전송하고, 연결 협상과 통화 상태는 인증된 서버 경로로 처리합니다. **수락한 탭만 통화를 제어**하도록 하며, 권한 요청 지연·취소·거절·재연결 과정에서 남는 마이크와 연결 자원을 정리합니다.

MongoDB의 조건부 갱신으로 서버 간 제어 상태를 공유하고, 실시간 이벤트가 늦게 도착하는 경우 활성 통화의 현재 상태를 대조하도록 보완했습니다. 실제 두 애플리케이션을 연결한 테스트로 통화 수락·종료·거절 흐름을 확인했습니다.

#### 5. 브로커·검색 확장과 운영 검증

기본 채팅 구조를 유지하면서 RabbitMQ STOMP relay와 Elasticsearch를 선택적으로 연결했습니다. 브로커의 목적지·헤더 처리 차이는 변환 계층으로 분리하고, **실제 브로커를 통과하는 회귀 테스트**로 검증했습니다.

검색은 메시지 변경을 비동기로 반영하고 삭제 상태와 재색인을 처리합니다. 운영 측면에서는 보호된 상태·지표 조회, 의존성 점검, 기존 DB를 덮어쓰지 않는 백업·복구 도구를 구성했습니다.

#### 6. 메시지 협업과 변경량 중심 동기화

메시지 반응·고정은 **원자적 상태 변경과 outbox 발행**을 연결했습니다. 반응은 사용자별 중복을 막는 명시적 추가/취소 API이며, 서버 채널의 고정은 현재 쓰기 권한이 있는 소유자·관리자만 변경합니다. 개인 북마크는 공용 메시지와 분리하고, 원본의 현재 내용·삭제 상태·방 접근 권한을 조회 시 확인합니다.

재접속 때 전체 대화를 반복 조회하던 흐름은 **방별 최근 1,000개 변경 기록과 불투명 커서**로 교체했습니다. 작성뿐 아니라 예전 메시지의 수정·삭제·반응·고정도 현재 상태로 대조합니다. 기록 범위를 벗어나면 오래된 캐시를 버리고 최신 100개부터 다시 시작하며, 이전 대화는 기존 이력 API로 조회합니다. 로그의 순번과 ID 배열을 같은 MongoDB 문서에서 함께 변경해 다중 워커의 순번 선점/기록 순서 뒤바뀜을 피했습니다.

브라우저가 메시지 본문을 영구 캐시하는 기능은 아니며, 발행 지연과 중복은 outbox의 재시도·버전 병합으로 처리합니다. 읽음 정보는 재접속 시 최대 1,000개의 보유 메시지만 따로 대조합니다. **구현으로 조회 범위를 제한했으며, 실제 처리량·지연 개선 수치는 아직 측정하지 않았습니다.** [설계·API·검증 상태](docs/MESSAGE_COLLABORATION.md)
